Архитектура

ASP.NET Core MVC на .NET 10 — монолит с разделением по слоям.

Слои приложения

Что делает

Классический слоёный монолит: тонкие контроллеры отдают View/JSON, вся логика склада — в сервисах, EF Core работает с БД. Razor-вьюхи в v6-дизайне (glass, токены тем).

FEFO-списание — OrderService.PlaceOrderAsync

Что делает

Проверяет заказ на доступность ингредиентов и списывает их из самых ранних партий (First Expired — First Out) в одной транзакции. При дефиците — отказ со списком нехватки, остатки не трогаются.

Как устроено
  • Разворот рецептуры: заказ → блюда → RecipeItem → требуемое количество каждого продукта.
  • Дефицит считается по живым партиям (QtyRemaining>0, ExpiresAt>now) — просроченные и ManualStopped блюдо отклоняют заказ с причиной («нужно 0.60, доступно 0.10» / «остановлено вручную: …»).
  • Списание по каждому продукту идёт от самой ранней ExpiresAt: уменьшает QtyRemaining, пишет WriteOff(reason="order"), не даёт уйти в минус (cap по остатку).
  • Всё в транзакции — либо весь заказ списался, либо ни одна строка.

Стоп-лист — GetStopListAsync

Что делает

Возвращает блюда, которые нельзя заказать: автоматически (не хватает ингредиента по рецепту) или вручную (Dish.ManualStopped с комментарием).

Как устроено
  • Авто: для каждого блюда проверяется хватает ли остатков живых партий хотя бы на одну порцию.
  • Ручной: ManualStopped=true + StopComment — снимается тумблером в «Остановить вручную» (поиск по блюдам).
  • Стоп-лист показывается на кухонном экране /Kitchen/{token} публично.

Hot Offers — HotOffersService

Что делает

Находит топ блюд, чьи ингредиенты скоро сгорят — то, что надо продать первым, чтобы спасти горящие партии.

Как устроено
  • Для каждого продукта ближайшая партия = его срочность (чем меньше часов до ExpiresAt, тем горячее).
  • Score блюда = функция срочности партии × доля этого ингредиента в рецепте блюда. Чем раньше истекает и чем больше продукта в блюде — тем выше.
  • Каждый оффер несёт объяснение: партия, часы, сколько продукта съест одна порция. Стоп-нутые блюда и просроченные партии исключаются.

Просрочка — ExpirySweepService

Что делает

Фоновый сервис раз в 60 секунд списывает истёкшие партии: обнуляет QtyRemaining и пишет WriteOff(reason="expired") — просрочка перестаёт считаться доступной.

Как устроено
  • HostedService с периодом 60 с; бежит по ресторанам, берёт партии с ExpiresAt<=now и QtyRemaining>0.
  • Списание фиксируется в журнале — потом попадает в аналитику потерь в ₽.
  • Ручное списание — отдельный путь (модалка на складе): количество + reason="manual" + комментарий.

Прогноз стоп-листа и закупки

Что делает

Оценивает, через сколько дней блюдо встанет в стоп при текущем расходе, и рекомендует, сколько заказать по фактическому потреблению.

Как устроено
  • Дневной расход продукта = списания по заказам за окно; запас в днях = текущий живой остаток / расход.
  • Блюдо в прогноз-стопе, если его лимитирующий ингредиент кончается быстрее всего.
  • Рекомендации закупок строятся по использованию за 7 дней — «заказать N кг» под факт.
Где в коде
Services/OrderService.cs · InventoryAnalyticsController (stop forecast, writeoff risk ₽)

Советник и ИИ — AdvisorService / Ask / AiInsight

Что делает

Собирает снапшот склада и либо спрашивает LLM (OpenAI-совместимый endpoint), либо работает по локальным правилам — всегда есть честный fallback.

Как устроено
  • Снапшот — GetSnapshotDataAsync: остатки, горящие партии, дефицит, потери, hot offers.
  • LLM — AskAiAsync: конфиг Ai:BaseUrl/Model/ApiKey; без ключа возвращает null → локальные правила.
  • Кэш — IMemoryCache (~7 мин) чтобы не дёргать LLM на каждый просмотр.
  • Почасовой — AiInsightService (HostedService): пишет AiInsight каждый час, дашборд читает последний без запроса к модели.
  • Чат — POST /Inventory/Ask {question} → snapshot+LLM → {answer}; /AnalyticsAi — вывод по статдампу периода.

SignalR + InventoryEventBus

Что делает

Изменения склада (заказ, списание, просрочка) пушатся клиентам — дашборд, склад, стоп-лист обновляются без перезагрузки.

Как устроено

  • Клиент — _InventoryRealtime.cshtml: SvRealtime.subscribe(name,fn) мягко обновляет виджеты; если SignalR недоступен — polling-фолбэк раз в ~60с.

Шпаргалка «вопрос → ответ»

10 вероятных технических вопросов жюри.

Q&A для защиты

Почему FEFO, а не FIFO?
FIFO списывает то, что пришло раньше; нам важнее что испортится раньше. Партия с 24ч уходит в заказ до партии с 72ч — меньше просрочки. Код: OrderService.PlaceOrderAsync.
Как избежали гонок при списании?
Вся проверка доступности + списание в одной транзакции EF: либо заказ списался целиком, либо ни одна строка. Минус невозможен — cap по QtyRemaining.
Что если LLM/API ИИ недоступен?
AdvisorService возвращает null → включаются локальные правила: hot offers, дедуп, рекомендации закупок работают без ключа. Кэш IMemoryCache гасит повторные запросы.
Как масштабировать на сеть из 100+ ресторанов?
RestaurantId на каждой сущности + индексы ({ProductId,ExpiresAt}, RestaurantId) — данные изолированы и запросы узкие. Орг-уровень (Organization) собирает точки, owner смотрит всю сеть.
Почему MVC, а не SPA?
Демо-скорость: Razor+SignalR даёт realtime без отдельного фронта и сборки. Меньше поверхности для багов на хакатоне, стили v6 инлайн-токенами.
Почему не Identity?
Ресторан — сменная работа, пароль не нужен: сотрудник получает access-код. Cookie-auth с клеймами AccessCodeId/OrganizationId/Role проще и безопаснее для демо.
Как работает авто-стоп?
GetStopListAsync проверяет: хватает ли живых партий хотя бы на одну порцию каждого ингредиента рецепта. Не хватает → блюдо в стопе до пополнения.
Как обновляется UI без перезагрузки?
SignalR-хаб /hubs/inventory + InventoryEventBus: события stock_changed/order_created/batch_expired мягко дёргают виджеты; если недоступен — polling-фолбэк.
Как не сломать прод при добавлении колонок?
На PG миграций нет — EnsureCreated + идемпотентные ALTER/CREATE на старте. Новая схема подтягивается сама, старая не падает.
Что считает score у hot offers?
Срочность партии (часы до истечения) × доля ингредиента в блюде. Чем раньше сгорит и чем больше его в рецепте — тем выше в списке.
